PART I: PROJECT OBJECTIVE, PRINCIPLES, AND ARCHITECTURAL SCOPE
================================================================================

1.1 THE MISSION OF CHRONO
Chrono is an Electron-based calendar, task manager, and cognitive assistant. It
was built to solve "organizer overwhelm" by pairing traditional scheduling tools
(calendars, task lists) with a local AI cognitive manager. This AI dynamically 
monitors the user's workload, focus time, and interaction rhythm, adapting its 
pacing, tone, and suggestions to support the user's mental bandwidth.

To make Chrono collaborative (enabling family accounts, shared calendars, cross-device 
synchronization, and cloud backup) while remaining highly performant and resilient, 
it requires a robust database sync pipeline.

1.2 THE ARCHITECTURAL DILEMMA: RELAY VS. DIRECT-TO-CLOUD
During its early development, Chrono utilized a multi-process architecture:
- Electron UI (Renderer Process)
- Electron Main (Node.js Process)
- Local Express API Server (Node/Express process running on http://localhost:5000)
- Prisma Client + Cloud PostgreSQL Database

In that relay setup, every cloud interaction (such as registering, logging in, 
fetching chat history, or syncing task calendars) followed a long loop:
1. The UI called `fetch('http://localhost:5000/api/...')`.
2. The Express server received the HTTP request, parsed the body, and verified the JWT.
3. Express invoked Prisma Client to perform queries against the remote PostgreSQL.
4. Prisma compiled the query, executed it over TCP/TLS, and returned the results.
5. Express formatted the data and returned it over HTTP.
6. The UI parsed the JSON and updated the view.

This was inefficient because:
- Launching and maintaining a separate Node.js Express server process alongside Electron 
  increased the local memory footprint and CPU overhead.
- Port 5000 is frequently blocked or used by other services (e.g. macOS AirPlay Receiver 
  or development servers), causing start-up crashes.
- Disrupted local networks caused local HTTP requests to fail, even though the database 
  servers were online.
- Distributing the app required packaging both the Electron app and the Express server, 
  multiplying packaging configurations.

1.3 THE SERVER-LESS SYNC VISION (DIRECT-TO-SUPABASE)
The current migration eliminates the local Express server. The Electron Main process 
is now the sole backend for the application. It:
1. Operates a local SQLite database (`chrono.db`) to ensure instant offline response.
2. Runs the Prisma Client directly inside Node.js.
3. Communicates with the UI via Electron IPC (`ipcMain` and `ipcRenderer`).
4. Executes sync pull and push reconciliations directly against the cloud database.
5. Manages authentication, profiles, and logs directly via Prisma.

2.1 LOCAL DATABASE: SQLITE (`main/main_db.js`)
The local SQLite database (`chrono.db`) is managed via the `better-sqlite3` library. 
It contains three main tables for scheduling:

1. `tasks` table:
   - `id` (TEXT PRIMARY KEY): UUID generated client-side.
   - `text` (TEXT NOT NULL): Description of the task.
   - `date` (TEXT NOT NULL): Target completion date (YYYY-MM-DD).
   - `calendar` (TEXT DEFAULT 'personal'): ID of the calendar layer it belongs to.
   - `completed` (INTEGER DEFAULT 0): Boolean representation (0 = active, 1 = completed).
   - `start_time` (TEXT): Planned start time (e.g., '09:30').
   - `duration_min` (INTEGER DEFAULT 60): Planned duration.
   - `updated_at` (INTEGER NOT NULL): Epoch millisecond timestamp of last change.
   - `device_id` (TEXT): Signature of the device that made the change.
   - `synced` (INTEGER DEFAULT 0): Sync status (0 = needs pushing, 1 = synchronized).
   - `deleted` (INTEGER DEFAULT 0): Soft-delete flag (0 = active, 1 = deleted).

2. `calendars` table:
   - `id` (TEXT PRIMARY KEY): UUID string.
   - `name` (TEXT NOT NULL): Label of the calendar (e.g., 'Study').

const cloudDb = require('./cloudDb');

async function pull({ lastSyncTime, deviceId, userId }) {
    if (!cloudDb) throw new Error("Supabase cloud database is not configured.");

    const lastSync = lastSyncTime ? BigInt(lastSyncTime) : 0n;
    const devId = deviceId || '';

    // Pull events created/modified since lastSyncTime by other devices
    const events = await cloudDb.event.findMany({
        where: {
            calendar: {
                members: { some: { user_id: userId, deleted: 0 } }
            },
            updated_at: { gt: lastSync },
            OR: [
                { device_id: null },
                { device_id: { not: devId } }
            ]
        }
    });

    const mappedEvents = events.map(e => ({
        id: e.id,
        calendar: e.calendar_id,
        text: e.text,
        date: e.date,
        completed: e.completed,
        start_time: e.start_time,
        duration_min: e.duration_min,
        updated_at: Number(e.updated_at),
        device_id: e.device_id,
        deleted: e.deleted
    }));

    // Pull calendars created/modified since lastSyncTime by other devices
    const calendars = await cloudDb.calendar.findMany({
        where: {
            members: { some: { user_id: userId, deleted: 0 } },
            updated_at: { gt: lastSync },
            OR: [
                { device_id: null },
                { device_id: { not: devId } }

    // Pull calendar memberships
    const members = await cloudDb.calendarMember.findMany({
        where: {
            calendar: {
                members: { some: { user_id: userId, deleted: 0 } }
            },
            updated_at: { gt: lastSync },
            OR: [
                { device_id: null },

async function push({ deviceId, userId, events, calendars, calendar_members }) {
    if (!cloudDb) throw new Error("Supabase cloud database is not configured.");

    // Reconcile calendars (newest-wins)
    if (calendars && calendars.length > 0) {
        for (const cal of calendars) {
            const existing = await cloudDb.calendar.findUnique({
                where: { id: cal.id },
                select: { id: true, updated_at: true }
            });
            if (!existing) {
                await cloudDb.calendar.create({
                    data: {
                        id: cal.id,
                        name: cal.name,
                        owner_id: cal.owner_id || userId,
                        layer_type: cal.layer_type || 'personal',
                        updated_at: BigInt(cal.updated_at),
                        device_id: cal.device_id,
                        deleted: cal.deleted ? 1 : 0
                    }
                });
            } else if (BigInt(cal.updated_at) > (existing.updated_at || 0n)) {
                await cloudDb.calendar.update({
                    where: { id: cal.id },
                    data: {
                        name: cal.name,
                        owner_id: cal.owner_id || userId,
                        layer_type: cal.layer_type || 'personal',
                        updated_at: BigInt(cal.updated_at),
                        device_id: cal.device_id,
                        deleted: cal.deleted ? 1 : 0
                    }
                });
            }
        }
    }

    // Reconcile calendar members (newest-wins)
    if (calendar_members && calendar_members.length > 0) {
        for (const mem of calendar_members) {
            const existing = await cloudDb.calendarMember.findUnique({
                where: {
                    calendar_id_user_id: {
                        calendar_id: mem.calendar_id,
                        user_id: mem.user_id
                    }
                },
                select: { updated_at: true }
            });
            if (!existing) {
                await cloudDb.calendarMember.create({
                    data: {
                        calendar_id: mem.calendar_id,
                        user_id: mem.user_id,
                        role: mem.role || 'viewer',
                        updated_at: BigInt(mem.updated_at),
                        device_id: mem.device_id,
                        deleted: mem.deleted ? 1 : 0
                    }
                });
            } else if (BigInt(mem.updated_at) > (existing.updated_at || 0n)) {
                await cloudDb.calendarMember.update({
                    where: {
                        calendar_id_user_id: {
                            calendar_id: mem.calendar_id,
                            user_id: mem.user_id
                        }
                    },
                    data: {
                        role: mem.role || 'viewer',
                        updated_at: BigInt(mem.updated_at),
                        device_id: mem.device_id,
                        deleted: mem.deleted ? 1 : 0
                    }
                });
            }
        }
    }

    // Reconcile events (newest-wins)
    if (events && events.length > 0) {
        for (const ev of events) {
            const existing = await cloudDb.event.findUnique({
                where: { id: ev.id },
                select: { id: true, updated_at: true }
            });
            const calId = ev.calendar_id || ev.calendar;
            if (!existing) {
                await cloudDb.event.create({
                    data: {
                        id: ev.id,
                        calendar_id: calId,
                        text: ev.text,
                        date: ev.date,
                        completed: ev.completed,
                        start_time: ev.start_time || null,
                        duration_min: ev.duration_min || 60,
                        created_by: userId,
                        updated_at: BigInt(ev.updated_at),
                        device_id: ev.device_id,
                        deleted: ev.deleted ? 1 : 0
                    }
                });
            } else if (BigInt(ev.updated_at) > (existing.updated_at || 0n)) {
                await cloudDb.event.update({
                    where: { id: ev.id },
                    data: {
                        calendar_id: calId,
                        text: ev.text,
                        date: ev.date,
                        completed: ev.completed,
                        start_time: ev.start_time || null,
                        duration_min: ev.duration_min || 60,
                        updated_at: BigInt(ev.updated_at),
                        device_id: ev.device_id,
                        deleted: ev.deleted ? 1 : 0
                    }
                });
            }
        }
    }

    return { success: true };
}

3.4 BACKGROUND SYNC LOOP ENGINE: `main/syncEngine.js`
--------------------------------------------------------------------------------
The background orchestrator. Runs as a background interval timer.
- Executes `performSync()` every 10 seconds.
- Performs SQLite `INSERT OR REPLACE` transactions to write updates from the pull 
  phase.
- Queries `synced = 0` rows from SQLite to construct the push payload.
- Clears the sync queue by updating `synced = 1` in SQLite once the push completes.
- Manages the `last_sync_time` metadata to ensure the next pull only fetches 
  changes made since the current sync cycle.

PART IV: OFFLINE-FIRST REPLICATION & CONFLICT RESOLUTION
================================================================================

4.1 NEWEST-VERSION-WINS LOGIC
In collaborative, offline-first systems, conflict resolution is critical. If 
Device A updates a task at time T1 while offline, and Device B updates the same 
task at time T2 while offline (T2 > T1), when both connect to the internet, 
the database must reconcile the states.

Chrono uses a **Newest-Version-Wins** policy:
- Every record has an `updated_at` column (millisecond epoch timestamp).
- When a change is made locally, the client sets `updated_at = Date.now()`.
- During sync push, the service queries the existing record's `updated_at`.
- If the incoming record's `updated_at` is greater, it updates the database.
- If the database's `updated_at` is greater, the update is discarded.
- During the next pull, the client retrieves the latest state from the database.

4.2 SOFT DELETION SYNCHRONIZATION
To prevent data loss and resolve conflict issues when deleting records, Chrono 
uses soft deletes.
- The `deleted` column is set to `1` on deletion, and `updated_at` is updated.
- The sync engine replicates the update to the cloud as a standard write.
- Other clients pulling modifications receive the record with `deleted = 1` 
  and mark their local records as deleted.
- The UI filters out deleted records during rendering.

5.1 JWT BRIDGING WITH `public.current_user_id()`
We created a custom PostgreSQL function `public.current_user_id()` to extract 
user IDs from both JWT payloads (used by web/Data API clients) and local 
session variables (used by direct pg connections):
```sql
CREATE OR REPLACE FUNCTION public.current_user_id()
RETURNS text
LANGUAGE sql
STABLE
AS $$
  SELECT COALESCE(
    nullif(current_setting('request.jwt.claims', true)::json->>'sub', ''),
    nullif(current_setting('request.jwt.claim.sub', true), '')
  )::text;
$$;
```

PART VI: RESOLVED TECHNICAL CHALLENGES
================================================================================

6.1 PRISMA 7 DELEGATION LIMITS (PRISMA 6 DOWNGRADE)
- **Problem**: Prisma 7 deprecated declaring connection parameters (`url` and 
  `directUrl`) directly in the `schema.prisma` datasource block, requiring they 
  be declared in a new `prisma.config.ts` configuration file instead.
- **Impact**: Prisma CLI commands (`db push`, `migrate dev`, `generate`) failed 
  with schema validation syntax errors, blocking compilation.
- **Resolution**: We downgraded to Prisma 6:
  ```bash
  npm uninstall prisma @prisma/client
  npm install prisma@6 @prisma/client@6 @prisma/adapter-pg@6
  npx prisma generate
  ```
  Prisma 6 natively supports these connection parameters in the schema 
  definition, resolving the issue.

6.2 PG DRIVER SSL OVERWRITE BUG
- **Problem**: When constructing a database pool, passing the connection string 
  and SSL options directly resulted in `self-signed certificate in certificate chain` 
  connection failures.
- **Root Cause**: The pg driver parses the connection string using the 
  `pg-connection-string` library. If the connection string contains `sslmode=require`, 
  it parses to `ssl: true`, overwriting the custom `ssl: { rejectUnauthorized: false }` 
  options.
- **Resolution**: We refactored `main/cloudDb.js` to parse the connection string 
  first:
  ```javascript
  const parse = require('pg-connection-string').parse;
  const config = parse(connectionString);
  config.ssl = { rejectUnauthorized: false };
  config.connectionTimeoutMillis = 5000;
  const pool = new Pool(config);
  ```
  This configuration prevents the options from being overwritten, ensuring secure 
  and error-free SSL connections.

6.3 WINDOWS FILE ACCESS LOCKS (EPERM ERRORS)
- **Problem**: Running `npx prisma generate` threw:
  `EPERM: operation not permitted, rename '...query_engine-windows.dll.node.tmp'`
- **Root Cause**: Windows locks binaries inside `node_modules` if they are 
  being held by active processes (like running Electron instances).
- **Resolution**: Terminated all active Electron processes before running generate 
  commands:
  ```powershell
  Stop-Process -Name electron -Force
  ```
